# G615LR Aura — the Linux-side investigation, full writeup

Companion to `README.md` (which covers the working Windows-side `0x04` protocol reference and the scripts in this folder). This document covers everything I've actually tried on Linux, what's confirmed working, what's confirmed not working, and the one lead that's still genuinely open.

## What actually works on Linux today

Two real, separate wins, both shipped and running:

**1. The classic `0x5d` protocol drives the whole chassis as one unit.** 5 of the 12 legacy modes work — `Static`, `Breathe` (colour1 only, colour2 is silently ignored by this firmware), `RainbowCycle`, `RainbowWave`, `Pulse`. The other 7 (`Star`, `Rain`, `Highlight`, `Laser`, `Ripple`, `Comet`, `Flash`) produce zero visible effect — confirmed this is a real firmware gap and not a packet bug: sending a working mode and a failing mode back to back gets byte-for-byte identical ACKs from the device either way. There's no independent zone control through this protocol — keyboard and the full 12-segment lightbar always move together.

Getting even this much working took fixing two mundane bugs, not a protocol mystery: the CLI and daemon binaries were version-mismatched (silently dropping color-set requests), and this hardware silently drops short `0x5d` Output-report writes that aren't padded to the full 64-byte size the HID descriptor declares.

**2. The `0x5d bc` "custom mode" protocol gives real independent per-zone keyboard control — a genuine breakthrough, previously unused for this device.** `rog-aura` already had this fully implemented for sibling per-key hardware (G634J/G635L), but G615LR's `aura_support.ron` entry had `advanced_type: r#None`, so nothing ever tried routing it there. Sending the real custom-mode init (`5d bc 00...`) followed by the zoned packet format lights the 4 keyboard zones independently — first time any zone control worked from code on this board. Lightbar codes in the same protocol don't respond (see below), but the keyboard zones are real and solid.

On top of that, I built and shipped a real software-effects feature: 7 procedural effects (`colour_cycle`, `strobe`, `comet`, `star`, `rain_drop`, plus the existing `breathe`/`static`), and two live-input modes — `music` (real FFT spectrum analysis over 4 frequency bands, one per keyboard zone, with auto-gain normalization and a sensitivity/decay curve matching how Armoury Crate's own sensitivity slider behaves) and `adaptive` (live on-screen colour sampling via `xdg-desktop-portal`'s ScreenCast API + PipeWire, not just a static wallpaper read). All CLI-only right now (`asusctl aura-fx <mode>`), no GUI exposure yet, keyboard zones only — the lightbar still isn't reachable through this path either.

Why the classic protocol's daisy-chain bleeds between kbd1/kbd4 and the adjacent lightbar zones (SingleZone-style whole-strip addressing) while the custom-mode protocol doesn't (genuine per-position addressing within the chain) — that's a real, understood architectural difference, not a bug in either.

## The `0x04` lightbar protocol: what's been ruled out

This is the actual unsolved part — independent, per-zone control of all 12 chassis lightbar segments, confirmed working on Windows (see `README.md`), never gotten to produce a visible effect from Linux across dozens of independently-tested hypotheses. Grouping by category, since a session-by-session list would just be noise:

**Packet content and transport — fully exonerated.** Byte-for-byte literal replays of real captured-working Windows bytes, a Rust unit test that asserts every packet the code builds matches a human-confirmed-correct 12-zone capture exactly, wire-level verification (via `usbmon`/Wireshark) that what the code intends to send matches what actually leaves the machine on the bus — all clean. Whatever's blocking this is not a packet-construction or transmission bug at any level of scrutiny.

**Interface and driver path — fully exonerated.** Tried both hidraw nodes explicitly, confirmed via `udevadm` which is genuinely the vendor interface, bypassed the kernel HID subsystem entirely via raw `libusb` control transfers (same null result), tried with the `hid_asus` kernel driver both attached and detached, tried against a stale-vs-freshly-resolved device node. No difference in outcome from any of it.

**Priming and animation-engine state — a real, understood mechanism, but not the fix.** The "priming" triplet everyone assumed was inert setup data is actually a real, successfully-applied `0x5d set-effect(RainbowCycle)+apply` command — every `0x04` test's baseline already has a genuine whole-chassis animation running underneath it. A 40-second continuous streaming test showed a subtle flicker synced to every `0x04` write, never resolving to a real colour — direct evidence the writes *are* landing and displaying for an instant, but the EC's own animation refresh loop overwrites them on its very next tick. Explicitly cancelling RainbowCycle first (a real `Static` `0x5d` command, confirmed working — the chassis genuinely went dark) and *then* streaming `0x04` produces a different but equally negative result: no flicker at all, meaning nothing gets displayed even briefly. Working theory: this firmware may only ever display `0x04`-written colour as a side effect of some *other* active mode's own refresh tick reading a shared buffer — with nothing ticking, nothing ever reads it. Tested every combination of {primed / not primed} × {static / genuinely animated changing frames} × {keyboard zone / lightbar zone} — all negative.

**The `0x0305` protocol — real, fully characterized, and a dead end for the lightbar specifically.** This turned out to be a completely separate, previously-uncharacterized mechanism: a continuously-streamed 10-byte packet (5-15Hz) that drives host-rendered Breathing/Strobing/Colour-Cycle animation on top of whatever the classic protocol set as a base colour — it's how those built-in animated modes work at all, since this firmware has no onboard animation engine (confirmed: even "Rainbow"/"Breathing" in Armoury Crate are Windows-side continuously recomputing and streaming fresh frames, not autonomous). Tried it standalone, after real priming, after establishing a real colour first, and interleaved with `0x04` zone writes — all negative, no distinguishable modulation. This might just be a genuine firmware gap on this specific board (matching the pattern of 7 of 12 classic modes also not working), or there's a prerequisite neither side of the investigation has found — Windows' own capture of this protocol never established where the modulated colour comes from either.

**Timing — checked properly, not just assumed adequate.** A real, carefully-measured test found the actual Windows visible-colour latency is roughly 8-12 seconds after streaming starts, not near-instant — meaningful, since most Linux tests only ran for 8 seconds. Re-ran with 40 seconds of continuous streaming: still just the flicker-and-overwrite pattern above, not a delayed success. Timing alone doesn't explain the gap.

**Batch size (`count`) — the one genuinely unresolved variable.** Every test up through most of this investigation sent one zone per packet. A byte-level analysis of real Windows captures (measuring per-byte-position frame-to-frame smoothness across hundreds of real writes, not guessing) confirmed the actual packet format generalizes cleanly: `count` (1-8 zones per packet), a 16-byte zone-ID region regardless of how many are actually used, then N×4-byte RGBA blocks starting at a fixed offset. Replicating a real, human-confirmed-working multi-zone capture *exactly* — a `count=5` packet with the 4 keyboard zones at near-zero alpha and one lightbar zone (`back_right`) at full alpha — **actually worked, live, wire-verified, twice.** This is the single most important result of the whole investigation: it's the first time `0x04` has done anything visible from code we wrote ourselves. But isolating it down to a `count=1` packet targeting only that same zone gave contradictory results on consecutive runs — dark the first time, lit the second time, with nothing else changed. That's a real, live, unresolved question: whether `count>1` is a genuine prerequisite, or the second run's success was carried-over EC state from the first successful multi-zone write. **The test that would actually resolve it and hasn't been run**: a genuinely fresh boot, zero prior `0x04` exposure that session, sending `count=1` to that exact zone as the very first thing touching it.

**Deeper platform-level checks — all dead ends, but worth having ruled out.** A full ACPI/WMI investigation (decompiling the live DSDT, probing candidate device IDs via `acpi_call`) found a real dispatch method matching the pattern Linux's own `asus_wmi` driver uses, but every probe including a known-working sanity-check ID came back "unsupported" — inconclusive on whether that's a real answer or an `acpi_call` encoding bug, not resolved either way. A Microsoft OS Descriptor really is present on this device (Windows-only mechanism, confirmed via a real `GET_DESCRIPTOR` query) but decodes to nothing more than a standard USB power-management hint, unrelated to driver selection. Kernel driver source review (`hid-asus.c`) confirms zero lightbar-awareness anywhere in the resume path — the kernel only ever restores keyboard-backlight brightness on wake, and a genuine suspend/resume cycle, captured live, shows nothing lightbar-related happening at all. Windows' own "Dynamic Lighting" feature (Settings-level, uses the standardized public HID LampArray spec on real LampArray hardware) does *not* talk to this device over that protocol — it's translated internally into the same proprietary `0x0305` stream, confirmed by capture, a real dead end worth having checked.

**Specific "missing init command" candidates — tried, all negative.** A community lead (from an asus-linux maintainer) suggested a distinct "go to direct mode" command separate from any handshake. Found and tried a plausible candidate (a single-byte boolean Feature report, ID `0x06`, sitting right next to the zone-write reports in the HID descriptor) — transport-level write succeeded, zero visible effect afterward. A genuine sleep/resume cycle captured on Windows revealed three previously-unseen `0x5d` subcommands (`0xc0`, `0xd1`, `0x9e`) plus a variant byte on an existing Output write — tried replaying all of them, both with and without the RainbowCycle-triggering priming triplet. One run produced an unexplained brief green flash during the setup phase (before any `0x04` write), but the actual zone write afterward still produced nothing over a full 20-second stream. Worth another look if it recurs, but not currently a working lead.

**Byte-position brute force of the working `0x5d bc` custom-mode protocol — exhausted, doesn't reach the lightbar.** Swept every plausible offset and every possible group-byte value (0-15) within that protocol's packet format, safety-scoped to only vary the colour-position byte (never touching a different report/subcommand, so no bricking risk). Result: groups 0 and 10-15 all produce the identical 4-keyboard-zone result regardless of group value — this firmware almost certainly just ignores the group/row selector entirely for this protocol, since the physical hardware only has 4 zones' worth of circuitry on this path. The lightbar is very likely not reachable through this protocol family at all, on any byte position — it's wired to a different controller.

**Cross-vendor research — nobody else has solved this either.** A sibling ASUS model (G614JZ) has a real, working per-key/per-LED-index protocol in OpenRGB, using a different byte layout than assumed here (raw start-index in the packet rather than a group/row encoding). Swept that exact index range on this hardware — only the keyboard zones respond at whichever indices map to the known keyboard zones; the chassis lightbar never reacts anywhere in the swept range. Real negative, but grounded in an actual working reference implementation rather than another guess. Broader research across other ASUS generations, other laptop vendors (MSI, Alienware, Razer, Legion, Omen), and other open-source RGB control projects found nothing directly transferable — this specific 16-zone independent-lightbar problem on this board appears to remain unsolved publicly, not just by me.

**One more unreproduced lead, worth a capture if it recurs.** During one of the shipped custom-mode keyboard-zone effects, the chassis lightbar was seen to flash briefly — contradicting the earlier finding that the custom-mode protocol never bleeds into the lightbar. Not investigated further at the time (no capture was running), so it's unconfirmed, but if it happens again, that's exactly the kind of accidental signal worth capturing immediately rather than letting pass.

## A new angle: isolating OS-level from driver-level

Everything above was tested at the HID/USB level — packets, transport, interface, timing. A different question hasn't been isolated yet: is the gap actually at the ACPI/WMI level, something Windows' own boot sequence does to the EC before any app or even any ASUS-specific driver loads, that Linux's boot sequence simply never sends?

The natural test is to strip a Windows install down to zero ASUS software (no Armoury Crate, no ASUS-specific drivers) and see if the keyboard/lightbar then behaves the same broken way it does on Linux. But that test has a real confound: Windows never runs with *zero* keyboard driver — its own generic HID stack (`hidclass.sys`/`kbdhid.sys`) takes over the moment the ASUS-specific driver is gone, and that's a different codebase from Linux's HID stack, doing its own USB enumeration and negotiation. A difference in behavior after stripping ASUS software wouldn't cleanly distinguish "something ASUS-specific was providing an unlock" from "Windows' own generic driver just negotiates the device differently than Linux's does, unrelated to ASUS."

The refinement: boot a Windows 10 install instead of Windows 11 for this test. Windows 10 predates the "Dynamic Lighting" feature entirely (a Windows 11-era addition, built on the standardized HID LampArray spec — already confirmed elsewhere in this investigation that this device doesn't actually speak LampArray anyway, it's translated internally into the same proprietary streaming protocol). A Windows-10-plus-zero-ASUS-software baseline is about as close to "just the OS's minimal generic HID handling, nothing else" as is realistically achievable, and worth wireshark-logging in full alongside the observed keyboard/lightbar behavior.

One other real hardware behavior worth knowing before running this: ROG-series boards (unlike TUF) reportedly keep their last LED state in EC memory — so if the keyboard shows some color/state that doesn't match anything currently running, that's likely leftover EC state, not a live driver doing something.

Not yet run. This is the next planned test.

## Where this actually stands

The `count=5`/`count=1` discrepancy above is the one genuinely open, high-value thread — everything else has converged on either a real working feature (keyboard zones, both protocols) or a thoroughly-exhausted negative result. If anyone wants to pick this up: a clean-boot, first-touch `count=1` test on the exact zone/colour that worked as `count=5` is the single test that would actually distinguish "batch size matters" from "carried-over device state" as the explanation — nothing else currently on the list would move this further. The OS-level isolation test above is the other open thread, still to be run.
